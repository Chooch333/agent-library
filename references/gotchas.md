# Gotchas — known tool traps

Shared reference for Project State and build tooling. Loaded by a skill's `requires:` header; not a trigger.

- **Pre-check parameter syntax on `write_status_snapshot`.** *(Until fixed in the MCP.)* The `project_slug` parameter on this tool is prone to malformed-tag slips that fail with "Project not found: 'undefined'." Verify all parameter tags are well-formed before submitting. If the call fails with that exact error, recognize it as a parameter-syntax slip and retry — do not search for a different cause. (Captured as Learning C-034 on `chat-protocol`.)
- **"No approval received" on a write tool → direct SQL fallback.** *(Until fixed in the MCP.)* When a Project State write tool (`write_plan`, `log_decision`, `review_plan`, `update_plan_status`, etc.) returns "No approval received," do not retry it a third time. Write the row via Supabase `execute_sql` against project `ujditldbqdiqigazkcak`, then confirm it landed with a **separate** SELECT — a row inserted inside a CTE is not visible to that same statement's final SELECT, so the check must be its own query. Rows written this way skip embedding, so they are findable by tag, project, status, or exact display ID (not semantic search) until re-embedded — say so in the handoff. Display IDs still auto-assign via trigger. The done receipt is still required on a direct-SQL flip to succeeded. (Captured as Lessons D-089 and CB-126.)
- **A freshly deployed or newly added MCP tool is not callable in the session that deployed it.** The tool manifest is fixed at connector-handshake time — a server redeploy, a brand-new tool name, and even opening a fresh chat are not enough on their own; the connector itself must be reconnected (toggled off/on) after the deploy, and even then the *building* chat's own toolset stays frozen mid-session. Budget for a fresh, reconnected session to make the first live call on any newly added MCP tool, and verify at the DB/logic layer (e.g. Supabase `execute_sql`) as a fallback when a same-session call is unavoidable. (Lessons E-080, E-085, E-222, D-083, CB-062/063, A-041 — six independent rediscoveries since June.)
- **GitHub Actions on these repos can go dark in more than one way — check before trusting silence, and protect work before a history rewrite.** Three distinct failure modes have each cost a build real time: a billing/spending lock where every run ends in 2–3 seconds with zero steps and no log (CB-427, CB-429/C-J-241); a workflow explicitly disabled in repo Settings → Actions — e.g. by a prior build's own setup step ahead of a `git filter-repo` history rewrite — which returns HTTP 422 on dispatch and creates no run at all (CB-496, C-J-325, C-J-330); and push-triggered runs that silently never fire during either outage and do not retroactively replay once Actions comes back, needing a manual re-dispatch (CB-438). Before treating a push or scheduled trigger as proof that work ran, check `list_workflow_runs` for a recent run rather than assuming silence means success. Before any build does a destructive git history rewrite (`filter-repo`, force-push) on a repo other builds depend on: pull the latest main immediately before rewriting, so a concurrent build's commits aren't dropped, and re-enable any workflow disabled for the rewrite before closing out — don't leave it for someone else to notice.
