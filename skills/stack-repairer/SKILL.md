# Stack Repairer

## What

The Stack Repairer fixes things that break while the stack is running, so Charles never gets a per-problem email and never has to kick off a fix. Once a day (17:29 Indianapolis) it reads the red and late dots the Stack Inspector (the 15-minute checker, `services/api/cron/stack-status.ts` in cbrain, which writes `stack_status`) has found, and the problems chats and runs have reported in its log, works out why each one broke, and fixes it at the smallest size that works: a re-run, a one-file fix, a short brief queued for tonight, or a brief built right away when it's urgent. It logs every action in `stack_repairs`, and the evening run sends Charles one short recap of the whole day. Per BB-2026-10-05-stack-repairer (Build 27).

**Two domains, one pair each.** The Rules Inspector / Rules Repairer (`skills/inspector`, `skills/repairer`) look after rules, skills and the stack map, weekly, through the Punch List. The Stack Inspector / Stack Repairer look after things running, daily. The Stack Inspector finds problems and grades fixes (by turning a dot green again); the Stack Repairer only diagnoses and fixes.

## When

**Fire when:**
- Invoked by name ("Stack Repairer: run").
- The Claude Code routine "Stack Repairer" fires (once a day, 17:29 America/Indiana/Indianapolis; replaced the hourly task on 2026-11-25).
- **Already-ran guard (first thing, before step 1).** A routine run ends at once and writes nothing (no rows, no run marker, no card, no email, the charter not read) when today's log already holds the day's recap run: `select 1 from stack_repairs where dot_id = '_run' and detail ? 'recap' and run_at >= date_trunc('day', now() at time zone 'America/Indiana/Indianapolis') at time zone 'America/Indiana/Indianapolis' limit 1` returns a row. This stops a duplicate fire; there is no hour window, so a run the scheduler starts late still does its work and sends the recap. A run invoked by name ("Stack Repairer: run") in a chat is never skipped and never sends the recap (step 7).
- **One run a day, what it costs** (oversight seat, Expert Desk report CB-797): the size-up ladder moves one step a day, a stalled email on the Email filing light waits up to a day for its redo, and a stopped Stack Inspector is noticed at the next run. Urgent work is still built in the same run (step 4b); briefs written at 17:29 make that night's build.

**Do NOT:**
- Edit rules, skills or the stack map (`concepts/stack-map.md`, any `SKILL.md`, any `references/` file, AGENT.md). That is the Rules Inspector / Rules Repairer's domain. A broken dot whose real fix is a rules or map change gets a `briefed` row and a short brief, never a direct edit.
- Review its own briefs (`review_plan`) or dispose its own disclosures (`dispose_judgment_call`).
- Email at any time other than the one daily recap (step 7).
- Turn the checker's per-problem alert emails back on (`ALERT_EMAILS_ON` in `services/api/cron/stack-status.ts` stays `false`).

## The `stack_repairs` log

One row per action. Columns: `id`, `run_at` (default now()), `dot_id`, `finding`, `action`, `detail` jsonb, `plan_id`, `commit_sha`, `outcome`.

- `action` is one of `rerun`, `cleared`, `fixed`, `briefed`, `built`, `needs-you`, `watching`, `graded`, `reported`.
- **Append-only — never UPDATE or DELETE a `stack_repairs` row.** Scheduled runs can't confirm edits to existing rows (first live run, 2026-10-07: both UPDATEs hung 3 minutes and saved nothing), so the log only ever grows. A grade is its own row: `action = 'graded'`, `dot_id` = the graded row's `dot_id`, `outcome` = `green` or `still-red`, `finding` = one line ("Re-run of world-graph worked — back to green"), `detail` = `{"grades": "<id of the graded row>", "evidence": "..."}`. An action row's own `outcome` column stays null; its grade is the newest `graded` row whose `detail->>'grades'` is its id.
- Every run also writes exactly one **run marker** row: `dot_id = '_run'`, `action = 'watching'`, `finding` = a one-line count ("3 red, 1 late — 2 acted on, 2 watched"), `detail` = `{"window": "07:00|12:00|17:00", "started_local": "<YYYY-MM-DD HH:MM, the run's start, Indianapolis time>", "red": [...ids], "late": [...ids], "repeats": [...dot or row ids not logged again], "recap_sent": true|false, "recap": "sent|nothing-to-send|error"}`, `outcome` left null forever. `started_local` is the local start time read for the skip rule. `recap` is on the 17:00 run's marker only: `sent` (the recap went out), `nothing-to-send` (every section was empty, so nothing was sent) or `error` (the send failed twice); Build 88's Gmail (out) light reads it. The Stack Repairer's own dot on the stack map checks the newest `run_at`, so a quiet day still shows the Repairer alive. Never grade a `_run` row.
- `detail` always carries `{ "evidence": "...", "size": "rerun|urgent-fix|brief|hard-gate|watch", "attempt": n }` plus whatever ids prove it (`run_id`, `deployment_id`, `workflow`, `ref`).

### Before any `needs-you`: the Hand it on test
A `needs-you` row says only Charles can clear it, so it must pass the "Hand it on" test (bin 4 of Closing out in `references/thread-checkin.md`) before it is written: the step is one of the charter's "Gates Claude works within" (money; his passwords, keys, sign-ins or a click his tools are refused) or "Talk with him first" (deleting data with no copy, sending in his name, changing one of his rules or settling two of his decisions that clash), or it needs a fact only Charles knows, or it is a click Claude tried and was refused. Fails the test → Claude handles it at the smallest size: `fixed`, `briefed` (a short brief, step 4c) or `watching`. Never a `needs-you` for "glance at", "confirm", "approve", a quiet source, or anything a build could do.

### No repeats
A dot or open row that already has a `needs-you` or `watching` row (any day, still ungraded) with the same evidence is not logged again. The run marker counts it in `detail.repeats` instead. New evidence (a newer failed run, a changed error, a new waiting item) is logged as usual.

## Reported problems

`stack_repairs` is also the stack fix log. A chat or run that notices a broken running part outside its own job files one `reported` row here, not a Comms Table post (AGENT.md). Design questions stay on the Comms Table.

**Row shape.** Insert only, through Supabase `execute_sql` on `lpeswznkxzeeyiqaewma`. No recheck, no row.
- `dot_id`: the nearest dot on the stack map, or `_unmapped`.
- `finding`: one plain line saying what is broken.
- `action`: `reported`.
- `detail`: `{"evidence": "...", "found_by": "<chat or run>", "recheck": "<a check anyone can run that passes once it is fixed; a count counts only records in their finished state (saved, filed, in the graph), never ones only fetched or tried>", "plan_id": "<optional, a plan that already covers it>"}`.

**Open rows.** A row is open when it has no `graded` row pointing at it and it is either `reported`, or a `needs-you` or `watching` row whose `detail` carries `reported_by` (rows logged by hand before this action existed).

**Handling.** An open row is treated like a red dot in steps 3 and 4: re-check the live state first, because the report may be stale. Every row a run writes about it carries `detail.reports` (the open row's id) and a copy of `detail.recheck`. One open row gets one action in flight: skip it while a row with that `detail.reports` is waiting on a grade.
- Fixable: the smallest size that works.
- A click only Charles can make, or a hard gate, that passes the Hand it on test above: `needs-you`.
- A plan already covers it: `watching` with `plan_id`. Step 3's second-`watching` rule does not apply; the plan is the brief.
- An ongoing condition (it can recur, not a one-off): the fix includes a real check on the map so it becomes a dot. That is a map change, so it is a `briefed` row, never a direct edit.
- A source that is quiet is an alert on its row on the Sources page and nothing else: no `stack_repairs` row at all. A real fetch error is still fixed (a moved or broken link is a one-file fix). Never a keep-or-drop question to Charles (Decision WG-213).

**Grading.** See step 2. An open `needs-you` row is not repeated each run; the original row stays open until its recheck passes.

## How

Read `references/charter.md` before the first step.

**1. Read.**
- *Precondition:* none — first step every run.
- *Action:* `select id, kind, label, state, own_state, reason, via_allowance, last_seen_at, checked_at, detail from stack_status where state in ('failing','late') and kind in ('dot','allowance')`. Skip `unknown` rows entirely (a `none` check or "couldn't check just now" is not a problem to fix). Also read the `_checker` meta row: if its `checked_at` is more than 45 minutes old, the Stack Inspector itself is down — treat `_checker` as a red dot named "Stack Inspector" (the evidence is cbrain-sync's Vercel cron `/api/cron/stack-status`). Then read today's log: `select * from stack_repairs where run_at >= date_trunc('day', now() at time zone 'America/Indiana/Indianapolis') at time zone 'America/Indiana/Indianapolis' order by run_at`. Then read the open reported rows, any day: `select r.* from stack_repairs r where (r.action = 'reported' or (r.action in ('needs-you','watching') and r.detail ? 'reported_by')) and not exists (select 1 from stack_repairs g where g.action = 'graded' and g.detail->>'grades' = r.id::text) order by r.run_at`.
- *Success evidence:* a list of red/late ids (possibly empty), today's prior rows and the open reported rows.
- *Recovery:* the query errors → retry once; if it still fails, write nothing else, and (only on the 17:00 run) put "Couldn't read the stack's status today" under Needs you in the recap.

**2. Grade earlier work.**
- *Precondition:* step 1 done.
- *Action:* find every ungraded action row: `action not in ('graded','watching')`, `dot_id <> '_run'`, and no `graded` row exists with `detail->>'grades' = id` (any day, oldest first). Compare each against the current `stack_status` row for that `dot_id`: state `ok` → insert a `graded` row with `outcome = 'green'`; state `failing`/`late` → insert a `graded` row with `outcome = 'still-red'`, but only if the dot's newest evidence is newer than the action's `run_at` (a re-run that hasn't finished yet is not still-red — write nothing for it yet). `briefed` rows stay ungraded until their plan has `succeeded` and the dot has been checked since. Never UPDATE the action row itself (see "The `stack_repairs` log").
- *Reported rows:* a row carrying `detail.recheck` is graded by running that recheck, not by its dot, and this includes the open `needs-you` and `watching` rows from step 1. Run the recheck as written and put the query and what it returned in detail.evidence; a count that includes records only fetched or tried does not pass. A recheck whose own wording counts records only fetched or tried is treated as a recheck that can't be run: it moves up to a short brief whose build runs a finished-state version. Passes → `graded` with `outcome = 'green'` and what the recheck showed in `detail.evidence`; a row with `detail.reports` and the open row it points at each get a grade. Fails → leave a `reported`, `needs-you` or `watching` row open with no grade; an action row (`rerun`, `fixed`, `built`) gets `still-red` under the rule above. A recheck that can't be run (from this run's tools) moves up to a short brief (step 4c) whose build runs it; log `briefed` with `detail.reports` and the plan id. A queued or running `stack-repairer` plan already covering that row → nothing new (No repeats).
- **Old asks.** Every `needs-you` row, any day, with no `graded` row whose `detail->>'grades'` is its id, reported or not (`select r.* from stack_repairs r where r.action = 'needs-you' and not exists (select 1 from stack_repairs g where g.action = 'graded' and g.detail->>'grades' = r.id::text)`) is re-run through the Hand it on test. Fails → insert `graded`, outcome `green`, `detail.graded_note` 'no longer needs Charles (Hand it on test)'; `close_thread` its card, closed_how 'nothing left for you'; then handle it at the smallest size (a quiet source → nothing; anything else → `fixed`, `briefed` or `watching`). A row on `email-approval-gate` always fails the test: the gate is gone, and a draft files itself labelled Inferred (charter 20; CB-628). Its card `job:stack-repairer-email-approval-gate` closes 'nothing left for you'.
- *Success evidence:* each newly graded action has a `graded` row pointing at it; a separate SELECT shows them.
- *Recovery:* a dot that no longer exists on the map → `graded` row with `outcome = 'green'` and `detail.graded_note = 'dot removed from map'`.
- **Size up on still-red.** A dot whose newest `graded` row today is `still-red` moves up one size this run: rerun → urgent fix (or brief if not urgent) → brief built now → one short brief for a build to dig in (once, No repeats); `needs-you` only when the Hand it on test passes. At most 2 re-runs per dot per day, ever.

None of these is a code bug. A billing lock is a hard gate (money) → `needs-you`. A disabled workflow: disabled on purpose (a build log or decision says so) → the dot's check is stale, so a short brief (map change). **4. Act — the smallest size that fixes it.**
- *Precondition:* a cause from step 3.
- **a. Re-run / clear.** A hiccup (network blip, flaky test, timeout, an outage that has ended) or a push-triggered job that never fired → `run_workflow` with an explicit `ref` (the branch the failed run used; `main` unless it says otherwise). Log `rerun`. If the failed thing has nothing to re-run but is already fixed upstream (e.g. a newer commit landed and the next scheduled run will clear it), log `cleared` with the commit. At most 2 re-runs per dot per day; the third time, go up a size.
- **b. Urgent fix.** Urgent = something has stopped that Charles would feel today, or data is piling up or being lost (email filing, intake, the site). If the cause is in one file and is clear, fix it directly: `replace_in_file` on the right branch (cbrain-ui → `review`, per CB-185; everything else → `main`), commit as Chooch333 (CB-121), never touch `apply.yml` (CB-103). Read the commit back, then re-run the failed job to prove it. Log `fixed` with `commit_sha`. If it's more than one file or the cause needs design, write a short brief (template below) and build it in this same run by following `skills/orchestrate-build/SKILL.md` (fetch it from agent-library). For an ongoing condition, the build fixes the failing part now; the check on the stack map goes in its own short brief (step 4c) for the night runner, so the Repairer's own run never edits the map. Log that brief as its own `briefed` row with its `plan_id`, beside the `built` row. Log `built` with `plan_id` and the last `commit_sha`.

## Progress tracking
Follows `references/thread-checkin.md` (naming convention and when to check in).
- kind: job
- build: the broken part's plain name + "repair", e.g. "Video intake repair" (thread_key "job:stack-repairer-<dot id>", or "job:stack-repairer-<row id>" for an `_unmapped` row; `source` "job")
- Opens when: a run logs `needs-you` that passed the Hand it on test (a hard gate only Charles can clear). Fixes, re-runs, `watching` rows and briefs don't need a card; briefs show on the Build Shelf
- Checks in: when a run leaves something open (next_step = the exact ask from the `needs-you` row, waiting_on `you`)
- Closes when: the dot's newest grade is `green`, or for a reported `needs-you` row its recheck passes (`close_thread`, closed_how "back to green"), or nothing on it waits on Charles (`close_thread`, closed_how "nothing left for you"; Closing out in `references/thread-checkin.md`)

## Examples

### Example 1: a flaky run
`world-graph` is failing: `ingest_transcript.yml` failed 40 min ago. The job log shows a network timeout fetching a transcript; the run before succeeded. Not urgent-sized; a re-run fits → `run_workflow` (world-graph, ingest_transcript.yml, ref main, the same inputs) → log `rerun`. The 12:00 run grades it `green`.

### Example 2: a real bug
The same workflow fails three times in a row with the same `KeyError` in one file. Two re-runs already used today → size up. Video intake has stopped (Charles would feel it today) and the cause is one line → fix on main, re-run, log `fixed` with the commit. If the cause spans files → short brief, built now via orchestrate-build, log `built`.

### Example 3: money
`anthropic-api` is failing (the pause flag says the credit balance is too low). Hard gate → log `needs-you`: "Top up Anthropic API credit — video and email intake are paused until then." It shows under Needs you in the 17:00 recap; no other email goes out.

## Pitfalls

- **Don't trust the reason text alone.** The checker's reason can flip between two checks of a list dot (Oct 5: Smoke tests read "failed 9 days ago" then "5 days ago"). Read the runs.
- **A billing lock or a disabled workflow is not a code bug** (`references/gotchas.md`, GitHub Actions rule). Re-running into a billing lock wastes nothing but proves nothing either.
- **Push-triggered runs don't replay after an outage** (CB-438). Re-dispatch them.
